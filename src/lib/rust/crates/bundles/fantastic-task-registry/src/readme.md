# task_registry — which agent or subtree holds which task

Verbs: reflect, add, assign, reassign, status, report, list, get. **Off by default**: a host registers this bundle only when `FANTASTIC_TASK_REGISTRY` is truthy, and an agent of it with no `task_store_id` in its record refuses every verb (`disabled`).

**What it is.** The task tree of a team of agents, and the audit of who holds each task and where it came from. It sits between agents and task sources (gh, jira, ...) as an extension, not an interface layer: it makes NO outbound call. `source` and `update_to` are opaque strings (`gh:owner/repo#12`, `jira:KEY-5`, anything); the LLM reads them to see where a task came from and where to push updates, then pushes them itself through that source's own agent. Nothing is synced automatically. `reflect` shows the agent tree; this registry is the task tree.

**An entry** is `{id, parent, source, update_to, holder, history, status, report, versions, source_version, fork_from, usage}`. `parent` is another task id or null. `holder` is an agent id, `{subtree: <root agent id>}`, or null; it must name an existing agent. `history` lists every change of holder as `{from, to, by, at}` (`by` is the caller, null for the operator); a step also carries the entry's `versions`, `source_version` and `fork_from` as set by that step, each only when non-empty (an entry without facts keeps the four plain keys). `status` is one of waiting, running, blocked, done, failed, paused (default waiting). `report` is the last report `{from, state, result, at, usage}` or null.

**Recorded facts** are plain, opaque strings the registry never checks against a repo or an agent. `versions` is `[{repo, branch, commit}]` (one per repo the task touches; exactly those three non-empty strings each; default `[]`), `source_version` is one opaque string (an issue's `updated_at`, a body hash; default null) and `fork_from` is `{agent, mark}` (two non-empty strings; the agent need not exist; default null). `usage` is `{input_tokens, cache_read_tokens, cache_write_tokens, output_tokens}` (non-negative integers) or null: the usage of the last `report` that carried one. A bad shape is `bad_arg` for that arg. An entry stored before these existed loads with the defaults and is rewritten with them at its next write.

**Verbs.**
- `add {id, source, parent?, update_to?, holder?, status?, versions?, source_version?, fork_from?}`: `update_to` defaults to `source`. Refused `exists` for a taken id and `not_found` for an unknown parent or holder. A holder given here is the first history item.
- `assign {id, holder, versions?, source_version?, fork_from?}`: only a task nobody holds; else `already_held`. A fact given here replaces the entry's value (`versions: []` clears the list); an absent one is left as it is.
- `reassign {id, holder, versions?, source_version?, fork_from?}`: only a held task; else `not_held`. Agent to agent, agent to subtree and subtree to agent are all allowed; every step is kept in `history`.
- `status {id, status?, versions?, source_version?, fork_from?}`: a state outside the six is `bad_arg`. This is how the lead updates the facts of a task (no history item is written; a changed value shows in history at the next assign or reassign). With none of the four given, `status` is `missing_arg`.
- `report {id, from?, state?, result?, usage?}`: records the last report. `usage` takes any of the four token keys (missing ones count 0; an unknown key, a negative, a float or a non-number is `bad_arg`); it is kept in `report.usage` and as the entry's `usage`. A report without usage leaves the entry's `usage` as it was. `from` defaults to the caller and must be the caller or one of its descendants, else `not_in_subtree`.
- `list {parent?, holder?, status?, ids?}`: `{tasks:[entry], usage:{input_tokens, cache_read_tokens, cache_write_tokens, output_tokens}}` sorted by id. `ids` keeps only those tasks (an id that is not a task is `not_found`; a non-list is `bad_arg`). `usage` is the sum of the returned tasks' last `usage`; a task that never reported usage counts 0.
- `get {id}`: the entry plus `children` (ids of the tasks whose parent is this id); an unknown id is `not_found`.

**Writers are branch leads.** The authority is the kernel call gate: only a lead (a subtree root) is granted the write verbs (`add`, `assign`, `reassign`, `status`, `report`) in its `can_call` on the registry, and the registry's `callable_by` lists it. A worker has no grant: it sends its lead the `report` message of `agentic_resources` and the lead writes the registry. The one rule inside the bundle is the `from` check of `report`.

**Storage is abstract.** The registry keeps its tables in the store agent its record names (`task_store_id`), through the store interface the agent memory uses (`append`, `read`). Each write appends one snapshot row `{kind:"task", task_id, content:<entry>}`; every read takes the latest row per `task_id`. The wiring is explicit, as for memory: the registry's `can_call` reaches the store and the store's `callable_by` lists the registry. A store is `ram_store` (lost at exit) or a durable one; one shared store for the agents and the registry is a CONFIG choice, never enforced here. The store keys rows by the calling agent, so two registries on one store never mix. Nothing is held in memory: a restart rebuilds from the store. A store that refuses or is unreachable gives `store_refused` with the store's own error; nothing falls back to RAM. Writes of one registry are serialized, so two leads cannot race.

**Refusals** are the kernel's one shape `{error: <sentence>, reason: <code>, hint?}`, so branch on `reason`: `disabled`, `store_refused` (also carries `store_error` and `store_reason`), `already_held`, `not_held` and `not_in_subtree`.
